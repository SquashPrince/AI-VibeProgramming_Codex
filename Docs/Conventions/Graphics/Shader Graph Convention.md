# Shader Graph 컨벤션

## 역할과 작업 범위

- [그래픽 공통 기준](<Common Convention.md>)을 따르며, 사용자가 에디터에서 직접 노드를 생성·작성·연결하는 것을 기본으로 한다.
- 에이전트는 설계·노드 선택·연결 안내, 기존 구성 파악과 문제 확인을 돕는다. 기본 사용법을 매번 반복하지 않고 새로운 기능과 버전 차이를 중심으로 설명한다.
- 사용자가 작성한 노드·연결·프로퍼티·Group·Sub Graph 등을 임의 수정·삭제하지 않는다.
- 변경이 필요할 때만 대상·이유·영향과 제안안을 설명해 확인받는다. 정리나 취향 차이만으로 바꾸지 않는다.
- 직접 제작·편집은 사용자가 요청하고 승인한 범위에서만 수행한다. 도구가 지원하는지 먼저 확인하며 MCP가 있다는 이유만으로 편집 가능하다고 단정하지 않는다.
- 승인 범위 안의 동일 변경은 반복 확인하지 않는다. 범위 밖 변경은 [승인 규칙](<../Safety/Approval Convention.md>)에 따라 추가 확인한다.

## 버전과 노드 확인

- 실제 Unity·URP·Shader Graph 패키지 버전을 확인한다. 설치 버전을 기준으로 노드명·포트·동작·메뉴 위치를 안내한다.
- 최신 공식 문서와 설치 버전의 차이를 확인하여 관련 변경이 있으면 구분해 설명한다. 최신 버전의 안내를 그대로 적용하지 않는다.
- 패키지에 포함된 문서·구현도 확인 근거로 사용할 수 있다. 구버전 영상이나 기억만으로 이름을 확정하지 않는다.
- 현재 버전에 없는 노드는 대체 방법과 차이를 설명한다. 이를 위해 패키지를 임의 업데이트하지 않는다.
- 동일한 버전·노드를 이미 확인했다면 반복 조사하지 않는다. 버전 변경·문서와 실제 UI 차이·새 의문이 생기면 재확인한다.

## 노드 설명과 연결 안내

- 일반 기능 → 이번 그래프의 역할 → 실제 입력·출력 연결 순서로 설명한다.
- 새 노드는 실제 이름, 입력값·자료형·출력 결과와 필요한 주의점을 안내한다. 설명 분량은 복잡도와 사용자 이해도에 맞춘다.
- 연결은 출발 노드와 출력 포트 → 도착 노드와 입력 포트로 명시한다. 같은 종류의 노드가 여러 개면 해당 역할을 함께 표기한다.
- 이미 설명한 노드는 현재 맥락의 역할과 달라진 부분만 짧게 설명한다.

### Lerp 안내 예시

**Lerp — 두 입력을 비율에 따라 섞는 노드**

A와 B를 T의 비율로 보간한다. T가 `0`이면 A, `1`이면 B, `0.5`이면 두 값의 중간값을 출력한다.
이번 구성은 강조 강도가 커질수록 원래 색이 피격 색에 가까워지게 하는 예시다.

| 출발 | 도착 |
|---|---|
| 원래 색 출력 | Lerp의 A |
| 피격 색 출력 | Lerp의 B |
| 강조 강도 출력 | Lerp의 T |
| Lerp의 Out | 이후 색상 처리 또는 실제 그래프에 적합한 최종 출력 |

Lerp 자체가 T를 자동으로 `0~1`로 제한하는 것은 아니다. 두 입력 사이로 제한해야 하면 그 요구에 맞는 처리를 설명한다.
연결할 채널 수·정밀도와 최종 출력은 실제 그래프에서 확인한다. 이 설명 형식과 분량을 모든 노드에 강제하지 않는다.

## 현황 파악과 확인 비용

- 저장된 `.shadergraph`·`.shadersubgraph`의 노드·프로퍼티·연결을 분석하고 필요하면 에디터 화면과 대조한다.
- 저장되지 않은 변경은 파일 분석에서 확인할 수 없다. 연결 분석은 컴파일·실제 화면 검증과 구분한다.
- 최초에는 필요한 전체 흐름을 파악하고 후속 작업에서는 변경·문제 영역을 우선 확인한다. 원문 전체를 대화에 출력하지 않는다.
- 전체 재검사는 구조 변경이나 미해결 문제가 있을 때 수행한다. Sub Graph·HLSL 의존성을 필요한 범위에서 추적한다.
- 시간·토큰·비용은 그래프 규모와 도구에 따라 달라진다. 항상 빠르거나 저렴하다고 보장하지 않는다.

## 노드 배치와 Group 정리

Group은 관련 노드를 시각적으로 묶는 기능이다. 별도 계산 에셋으로 만드는 Sub Graph와 구분한다.

- 기본은 노드 이동·Group 구성안을 제안하고 사용자가 직접 정리하는 방식이다.
- 사용자가 직접 정리를 요청하면 도구의 가능 범위, 대상, 확인·편집·검증에 필요한 예상 시간·토큰·비용 부담을 설명한다. 정확한 산정이 어려우면 추정임을 명시한다.
- 일부 영역과 전체 정리의 범위를 비교해 불필요한 작업을 줄인다.
- 정리는 배치·Group 구성에 한정한다. 계산·연결·프로퍼티 등 기능 변경이 필요하면 별도 제안·승인을 받는다.
- 기존 배치를 무조건 재정렬하거나 Group을 의무적으로 추가하지 않는다.

## 프로퍼티 생성과 정돈

Blackboard의 프로퍼티는 입력값 정의이며, 작업 영역에 배치한 Property 노드는 그 값을 읽어 전달한다. Sub Graph를 뜻하지 않는다.

- 외부에서 조절할 값과 내부 계산값을 구분한다. 불필요한 프로퍼티 생성·Material 노출을 피한다.
- 생성 전에 기존 항목과 이름 충돌·사용처를 확인하고 이름·용도·자료형·기본값·필요한 범위·단위·배치 위치를 작업 단위로 묶어 제안한다.
- 표시 이름과 스크립트 등이 접근하는 Reference 이름을 구분한다. Inspector의 조절 범위와 실제 계산값 제한도 구분한다.
- [기존 명명 규칙](<../Code/Code Convention.md>)을 따르고 기술 식별자의 요구사항을 확인한다. 표시 이름·Reference의 세부 표기법이 미정이면 생성 제안에서 확인하며 예시를 고정 규칙으로 만들지 않는다.
- 역할이 명확한 최소 길이를 사용한다. `HitStrength`, `BaseColor`, `AlphaMask`는 예시다. `_MaterialColorChangeWithTextureAlpha`처럼 처리 과정을 문장으로 나열하지 않는다.
- 긴 설명은 설명란·문서에 두고 의미를 알기 어려운 약어로 줄이지 않는다.
- 기존 항목은 의미 혼동·중복·분산 등 구체적인 관리 문제가 있을 때 정리를 제안한다. 단순 개수나 모호한 수준을 기준으로 일괄 정리하지 않는다.
- 변경·삭제는 그래프 연결·Material·스크립트 사용처와 영향을 확인해 승인받는다.

### 프로퍼티 제안 예시

| 항목 | 예시와 의미 |
|---|---|
| 표시 이름 | HitStrength: 피격 색 강조 강도 |
| Reference | _HitStrength: 스크립트 접근용 이름의 제안 예시 |
| 자료형 | Float: 숫자 하나 |
| 기본값 | 0: 강조하지 않음 |
| 조절 범위 | 0~1: 원래 색에서 피격 색까지 혼합 |
| 배치 | 관련 피격 효과 프로퍼티 가까이 |

## Sub Graph

Sub Graph는 노드로 구성한 계산을 별도 에셋으로 만들고 다른 그래프에서 하나의 노드처럼 사용하는 기능이다.

- 실제 재사용이나 복잡한 계산의 독립 관리가 필요할 때 제안한다. 노드 수만으로 분리하지 않는다.
- 단순 시각적 정리는 Group, 계산을 별도 에셋으로 관리할 필요가 있으면 Sub Graph를 검토한다.
- 생성 전 분리할 계산·입력·출력·사용처·분리 이유를 설명한다.
- 이름과 포트는 짧고 역할이 명확하게 제안한다. 적절한 기존 Sub Graph가 있는지 먼저 확인한다.
- 공유 Sub Graph 변경 전에는 사용하는 그래프와 영향을 조사해 승인받는다.
- 사용자 직접 작성·연결을 기본으로 하고, 직접 제작·수정은 별도 요청·승인 범위에서 진행한다.
- 분리 자체를 성능 최적화로 설명하지 않는다. 주된 목적은 재사용과 구성 관리이며 성능은 별도 검증한다.

## Custom Function

기본 노드는 제공된 계산, Sub Graph는 노드 계산의 묶음, Custom Function은 HLSL 계산을 호출하는 연결점이다.

- 기본 노드·Sub Graph로 가능한지 먼저 검토한다. Custom Function이 더 적합하면 이유와 대안을 설명한다.
- 코드 길이만으로 선택하지 않고 이해·편집·재사용·유지보수 편의를 함께 판단한다.
- 계산 목적·입력·출력·자료형·연결 위치를 설명한다. 코드는 [HLSL 기준](<HLSL Convention.md>)을 따른다.

| 방식 | 작성 위치 | 제안 시 고려할 점 |
|---|---|---|
| String | 노드 설정의 Body에 함수 본문 입력 | 그래프 안의 작은 계산, 그래프에 포함되는 코드의 관리 편의 |
| File | 별도 HLSL 파일을 Source로 연결 | 파일 단위 설명·수정·재사용, 다른 사용처의 영향 |

- 설치 버전의 함수 이름·정밀도·포트 형식을 확인한다. File 방식에서는 노드 Name과 코드의 `_float`·`_half` 접미사를 구분해 설명한다.
- 노드·포트·연결은 사용자 작업을 기본으로 한다. HLSL 파일은 승인 범위에서 에이전트가 작성할 수 있다.
- 기존 파일·함수 변경은 사용처·영향 확인과 승인을 거친다.

## 최적화와 사용자 테스트

- 생성되는 계산과 Texture 샘플링 등 실제 비용을 검토한다. 노드 수·Group·Sub Graph 수만으로 성능을 판단하지 않는다.
- 정밀도·분기는 [HLSL](<HLSL Convention.md>), 샘플링·Variant·Overdraw는 [Shader](<Shader Convention.md>), 배칭은 [Material](<Material Convention.md>)의 설명을 참조한다.
- 새 관련 기법을 안내할 때는 개념·조건·장단점·검색어·테스트 방법을 제공한다. 공통 절차는 [성능 컨벤션](<../Safety/Performance Convention.md>)을 따른다.
- 사용자 연결 후 노드 오류, 프로퍼티 조절, Material 적용, 실제 효과의 테스트 순서를 안내한다.
- 컴파일·연결·화면·성능을 구분해 보고한다. 결과를 확인하지 못한 단계는 미검증으로 남긴다.
