# 이미지 생성 컨벤션

## 목적과 적용 범위

사용자가 제공한 레퍼런스를 분석하고 질문과 답변으로 방향을 확정한 뒤, 승인한 이미지만 생성하거나 편집한다.
무분별한 생성과 에이전트의 임의 해석을 줄이고, 시안 검수와 후속 수정을 단계별로 진행한다.

이 문서는 래스터 이미지의 신규 생성과 기존 이미지 편집에 적용한다. 사운드 작업은 별도 규칙에서 다룬다.
생성 결과를 Unity에 임포트하거나 프로젝트에 연결하는 작업은 별도 요청과 승인 범위다.

## 기존 규칙과 도구 지침

- 이미지 생성과 편집 작업에서는 이 문서를 먼저 읽고, 현재 제공되는 `imagegen` 스킬과 실제 도구 사양을 확인한다.
- 일반 도구 지침이 레퍼런스 없는 생성, 창의적 보완이나 반복 개선을 허용하더라도, 이 프로젝트에서는 아래 레퍼런스 필수 조건과 방향 승인 및 사용자 검수 절차를 적용한다.
- 설명과 기존 에셋 검토는 [그래픽 공통 규칙](<Common Convention.md>), 파일 생성과 변경 승인은 [승인 범위](<../Safety/Approval Convention.md>)를 따른다.
- 기존 SVG나 코드로 편집할 수 있는 단순 도형, 아이콘과 UI 요소는 이미지 생성과 비교해 적합한 방법을 제안한다. 사용자가 선택한 제작 방식을 임의로 바꾸지 않는다.
- 실제 생성 도구의 지원 범위를 확인하고 수행할 수 없는 편집이나 출력 조건을 보장하지 않는다.

## 레퍼런스 필수 제공

- **사용자가 레퍼런스가 될 이미지를 제공하지 않았다면 생성하지 않는다.** 원하는 이미지를 설명한 문장만으로 생성에 착수하지 않고 이미지 제공을 요청한다.
- 대화에 첨부한 이미지나 사용자가 지정한 접근 가능한 이미지 파일을 확인한다. 경로만 알고 실제 이미지를 보지 못한 상태를 분석 완료로 보고하지 않는다.
- 앞서 사용자가 제공했고 이번 작업에도 쓰기로 확인된 레퍼런스는 다시 제출하도록 요구하지 않는다.
- 에이전트가 임의로 찾은 이미지를 사용자 제공 레퍼런스 대신 사용하지 않는다.
- 각 이미지가 신규 생성의 참고인지, 직접 편집할 대상인지, 합성에 넣을 소재인지 구분한다.
- 여러 이미지라면 각 이미지에서 참고할 요소를 개별적으로 확인한다. 서로 충돌하는 특징을 임의로 조합하지 않는다.

## 분석과 질문

- 레퍼런스의 구도, 실루엣, 색감, 질감, 표현 방식과 배경을 분석한다. 용도와 관련된 특징을 중심으로 설명한다.
- 화면에서 확인한 사실과 에이전트의 해석을 구분한다. 보이지 않는 부분이나 원작자의 의도를 사실처럼 단정하지 않는다.
- 사용자에게 어떤 특징을 유지하고 무엇을 바꿀지 질문한다. 색감만 참고하는지, 같은 대상을 다른 자세로 표현하려는지 등을 구분한다.
- 용도, 필요한 크기와 비율, 투명 배경 여부, 정확히 들어갈 글자, 포함 또는 제외할 요소 중 미확정인 부분을 확인한다.
- 질문은 결과에 영향을 주는 사항에 집중한다. 이미 답변한 내용은 반복 질문하지 않는다.
- 사용자 답변을 반영해 분석과 질문을 필요한 만큼 이어가고, 확인되지 않은 시각적 선택을 임의로 확정하지 않는다.

### 분석 후 질문 예시

아래는 두 레퍼런스를 제공한 경우의 예시다. 실제로 확인한 특징으로 바꿔 안내한다.

> 첫 번째 이미지에서는 어두운 파란색 계열과 금속 질감을 확인했습니다. 두 번째 이미지는 윤곽이 단순하고 작은 크기에서도 형태가 드러납니다.
>
> 1. 첫 이미지의 색감과 두 번째 이미지의 형태를 참고하는 것이 맞나요?
> 2. 원본과 같은 무기를 표현할까요, 색감과 표현 방식만 참고해 다른 무기를 만들까요?
> 3. 게임 아이콘으로 사용할 예정이라면 배경을 투명하게 할까요?

## 생성 방향 확정과 사전 보고

- **사용자 답변으로 방향을 정리하고 승인받기 전에는 생성 도구를 호출하지 않는다.**
- 보고에는 레퍼런스별 역할, 유지할 특징, 변경할 특징, 제외할 요소, 용도, 수량과 출력 조건을 포함한다.
- 미리보기만 할지 프로젝트에서 사용할 파일인지 구분하고, 파일을 저장할 경우 경로와 기존 이름 충돌을 확인한다. 구조와 명명은 [구조 규칙](<../Work/Structure Convention.md>)을 따른다.
- 승인한 요구를 생성 지시문에 명확하게 옮긴다. 사용자가 요구하지 않은 장식, 사물, 색상이나 서사를 임의로 추가하지 않는다.
- 이미 명확한 요구는 의미를 바꾸지 않고 정리한다. 생성에 필요한 미확정 요소가 남았다면 먼저 질문한다.
- 출력 크기나 형식 등 도구가 직접 지원하지 않는 조건은 한계를 설명하고 필요한 후속 작업과 승인 범위를 정한다.
- 토큰, 도구 크레딧, 생성 대기 시간과 후속 편집 작업량을 구분한다. 확인할 수 없는 비용과 정확한 사용량을 임의로 수치화하거나 무료라고 단정하지 않는다.

### 생성 전 보고 예시

> 무기 아이콘 시안 1개를 만들겠습니다.
>
> - 레퍼런스 역할: 첫 이미지의 색감, 두 번째 이미지의 단순한 형태
> - 유지: 어두운 파란색 계열과 금속 질감
> - 변경: 사용자가 선택한 무기 형태
> - 제외: 글자, 로고와 배경 장식
> - 출력: 승인한 비율과 크기, 투명 배경
> - 작업: 시안 1개 생성 후 검수 대기
>
> 이 방향으로 생성할까요?

## 생성 수량과 검수 대기

- 기본은 한 번에 시안 1개다. 여러 시안은 필요한 수량과 서로 비교할 차이를 설명하고 승인받는다.
- 선택하지 않은 다른 구도나 스타일을 추가로 생성하지 않는다. 여러 안을 한 장에 담는 방식으로 수량 승인을 우회하지 않는다.
- 승인한 범위로 생성한 뒤 결과를 확인하고 사용자에게 제시한다.
- 결과가 마음에 들지 않을 것 같거나 요구와 다른 부분을 발견했더라도 자동 재생성하지 않는다. 차이를 설명하고 사용자 검수를 기다린다.
- 여러 에셋이 필요하면 대표 이미지의 방향을 먼저 확정하고, 후속 요청과 승인에 따라 확장한다. 첫 이미지의 승인을 나머지 전부의 생성 승인으로 확대하지 않는다.

## 수정과 기존 파일 보호

- 수정 요청에서는 바꿀 부분과 유지할 부분을 정리한다. 변경점이 명확하고 승인 범위 안이면 같은 내용을 재질문하지 않고 편집한다.
- 기존 결과를 유지하며 일부만 바꾸는 요청은 편집 작업으로 다룬다. 단순 참고 이미지로 삼아 전체를 새로 생성하는 방식으로 임의 대체하지 않는다.
- 편집 지시에는 유지할 구도, 대상, 색감 등 필요한 불변 조건을 명시한다. 편집 결과가 원본과 완전히 동일하게 보존된다고 보장하지 않는다.
- 구도나 스타일 등 확정한 방향을 바꿔야 한다면 이유와 영향을 설명하고 확인받는다.
- 원본과 승인된 결과는 수정 지시 없이 덮어쓰거나 삭제하지 않는다. 변경본은 승인된 별도 경로와 이름으로 보존하는 방식을 제안한다.
- “색을 파랗게 바꿔줘”라는 요청을 구도 변경이나 다른 스타일의 시안 추가로 확대하지 않는다.
- 편집용 로컬 이미지는 실제로 열어 확인하고 도구의 참조 입력에 포함한다. 이전 생성 결과를 편집 대상으로 쓰는 경우도 어떤 이미지를 편집하는지 명확히 한다.

## 도구 선택과 사용 조건

- 새로 생성하기, 사용자 제공 이미지 편집하기, 기존 자료 활용하기 중 실제 요구에 적합한 방법을 비교한다.
- 별도 요청이 없으면 외부 도구는 무료 사용 가능 후보만, 기존 콘텐츠 에셋은 CC0이면서 무료인 것만 추천한다.
- 외부 도구를 추천할 때 실제 작업에 필요한 무료 범위, 유지보수 상태, 출력 제한과 사용 조건을 확인한다. 추가 설치와 계정 설정은 사용자가 수행하도록 안내한다.
- 생성 도구는 무료 이용 범위, 생성물 이용 조건, 상업적 사용 조건과 표시 의무를 공식 자료로 확인한다. **생성됐다는 이유로 결과를 CC0이라고 간주하지 않는다.**
- 사용자 제공 이미지도 권리와 라이선스를 자동 확보한 것으로 간주하지 않는다. 출처와 사용 조건이 불명확하고 작업에 영향을 주면 필요한 사항을 확인한다.
- 서비스 조건은 바뀔 수 있으므로 구체적인 도구 도입과 배포 용도 판단 시 최신 공식 자료를 확인한다. 확인하지 않은 법적 이용 가능성을 보장하지 않는다.
- 내장 도구를 사용할 때 별도 API 키를 요구하지 않는다. 실제 사용 가능한 내장 도구와 `imagegen` 스킬을 우선 확인한다.
- 내장 도구 실패나 미지원 조건 때문에 외부 API 또는 CLI로 조용히 전환하지 않는다. 필요한 조건과 비용을 설명하고 사용자가 해당 경로를 명시적으로 선택한 경우에만 검토한다.

## 결과 검수와 파일 전달

검증 공통 절차는 [테스트 규칙](<../Safety/Testing Convention.md>)을 따른다. 아래 항목에서 용도와 관련된 것만 확인한다.

| 확인 대상 | 확인 내용 |
|---|---|
| 승인 방향 | 레퍼런스의 선택한 특징, 구도, 대상, 스타일과 색감 |
| 요청 범위 | 포함할 요소, 제외할 요소, 정확한 글자와 수량 |
| 출력 조건 | 실제 파일 크기와 형식, 승인한 비율 |
| 투명 배경 | 실제 투명도와 가장자리, 배경 무늬가 투명도처럼 그려진 것은 아닌지 |
| 게임용 식별성 | 사용할 작은 크기에서도 형태가 드러나는지, 다른 에셋과 스타일이 어울리는지 |
| 편집 보존 | 변경 요청 외에 유지해야 할 요소가 달라졌는지 |

- 직접 확인한 파일 속성과 눈으로 본 결과를 구분한다. 실제 Unity 표시와 성능을 확인하지 않았다면 미검증으로 남긴다.
- 요청과 다른 부분과 한계는 설명한다. 자동 재생성하지 않고 사용자의 유지, 수정 또는 재생성 지시를 기다린다.
- 결과 보고에는 사용한 레퍼런스의 역할, 생성 또는 수정 내용, 최종 생성 지시문, 사용 도구, 수행한 검사와 남은 확인을 포함한다. 긴 내용은 간결하게 정리하거나 확인 가능한 기록으로 제공한다.
- 미리보기 이미지를 최종 프로젝트 파일로 간주하지 않는다. 프로젝트용으로 승인한 결과는 사용자가 지정한 위치 또는 승인된 작업 공간 경로에 보존하고 실제 경로를 안내한다. 도구 기본 저장 위치에만 두고 프로젝트 적용이 끝났다고 보고하지 않는다.
- 생성 결과를 저장하는 것과 프로젝트 에셋으로 임포트하는 작업을 구분한다. `Assets` 배치와 관련 메타데이터 등은 기존 승인 규칙을 따른다.
- Texture 임포트와 압축은 [Texture 규칙](<Texture Convention.md>), Sprite 분할과 Pivot 등은 [Sprite 규칙](<Sprite Convention.md>)을 참조한다. 별도 요청 없이 해당 설정과 프로젝트 연결까지 수행하지 않는다.
