# 테스트·검증 컨벤션

> 상태: 공통 운영 기준.
> 대상: Unity/C# 기반 AI 보조 개발. 기존 승인 규칙과 사용자 확정 사항을 유지한다.

## 목적
변경 위험에 맞는 검증을 수행하고 예상과 실제 실행 결과를 구분한다.

## 검증 선택
| 변경 | 기본 확인 |
|---|---|
| 순수 계산·상태 전이 | 정상값·경계값·중요 실패 조건 |
| 생명주기·이벤트 | 활성화·비활성화·재진입·종료 |
| UI·입력 | 대상 입력 장치·화면 조건에서의 동작 |
| Scene·Prefab·설정 | 참조 누락·영향 Scene·필요한 빌드 |
| 문서·서식 | 내용·경로·변경 범위 |

## 규칙
- 기존 테스트와 실행 방법을 먼저 확인한다.
- 반복 회귀 위험이 있는 로직은 자동 테스트를 검토한다. 구현을 그대로 반복하는 테스트는 늘리지 않는다.
- Unity 의존성이 없는 로직 검증과 실제 런타임 연결 검증을 구분한다.
- 테스트 통과를 위해 요구 동작을 완화하거나 실패 코드를 숨기지 않는다.
- 변경 위험에 맞는 기존 기능을 확인하고 불필요한 검증 반복은 피한다.

## Unity 최소 검증 기준
- 코드 변경은 Unity 스크립트 컴파일 후 새 오류가 없는지 확인한다. 작업 전부터 있던 오류는 가능한 범위에서 기록하고 이번 변경으로 추가된 오류와 구분한다. 구분할 수 없으면 그 한계를 보고한다.
- 변경 기능의 실행 순서·입력·예상 결과를 정하고 실제 동작을 확인한다. 문서만 변경한 경우에는 위 `검증 선택`의 문서·서식 기준을 적용한다.
- 에이전트가 직접 수행한 검증과 사용자가 Unity에서 수행해야 하는 검증을 구분한다. Unity 제어 도구나 실행 환경이 없으면 사용자에게 확인 절차와 예상 결과를 제공한다.
- 실행하지 못한 항목은 미검증으로 남기고 검증 완료로 보고하지 않는다. 완료 판정은 [완료 조건 컨벤션](<../GitHub/Completion Convention.md>)을 따른다.
- 자동 테스트 도구·CI·성능 측정 환경 도입은 필수 착수 조건이 아니다. 관련 작업에서 필요해지면 도입 여부와 실행 방법을 정한다.

## 결과 기록
환경·대상·실행 방법·기대 결과·실제 결과를 남긴다. 성공·실패·미실행을 구분하고 실패 재현 조건을 적는다.
코드를 읽은 판단을 Unity 실행 확인이나 테스트 통과로 표현하지 않는다.

## 프로젝트별 값
확정 값은 [프로젝트 값](<../../Project Values.md>), 미확정 값은 [프로젝트 설정](<../../Project Configuration.md>)을 따른다. 미확정 값의 확인 · 등록은 `project-setup` 스킬로 수행한다.
