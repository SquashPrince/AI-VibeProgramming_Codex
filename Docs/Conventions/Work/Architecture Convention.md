# 설계 컨벤션

## 작업 전 보고
- 설계 구조를 정하거나 변경하는 작업은 착수 전에 현재 구조와 제안 구조, 클래스별 책임, 의존성·통신 방식, 영향 파일과 검증 방법을 사용자에게 보고하고 승인을 받는다.
- 영향 파일은 `수정 파일`과 `생성 파일`을 구분하고, 각 파일의 변경 내용을 목록으로 적는다. 해당하는 파일이 없으면 `없음`으로 표시한다.

## 설계 원칙
- 기본은 요구사항을 충족하는 가장 단순한 구조로 한다. 구현 교체·복수 구현·구독자 분리 등 구체적인 필요가 있을 때 인터페이스·이벤트를 검토한다. SOLID를 적용하기 위한 목적만으로 타입을 추가하지 않는다.
- 아래 원칙은 실제 요구사항에 필요한 범위에서 적용한다.
```text
- 단일 책임 원칙 : 기능을 지나치게 작은 단위의 짧은 클래스로 많이 나누지 않는다. 예를 들어 이동·점프·공격·방어·스킬을 각각 작은 클래스로 나눠 관리 부담이 커졌다면, 실제 책임과 변경 이유가 가까운 기능을 역할 단위로 묶을지 검토한다. 병합 전에는 합칠 클래스, 묶는 이유, 유지할 동작과 영향받는 파일을 사용자에게 보고하고 승인을 받는다.

- 개방-폐쇄 원칙 : 기존 동작과 공개 계약에 영향을 주지 않는 범위에서 기능을 확장한다. 새 타입이나 추상화는 실제로 구현 교체·복수 구현 등이 필요한 경우에 검토하며, 기존 클래스 수정이 더 단순하고 안전하면 그 방식을 선택할 수 있다.

- 리스코프 치환 원칙 : 여러 하위 구현을 같은 계약으로 다뤄야 할 때 각 구현이 호출자가 기대하는 동작을 지키는지 확인하고 공통 부모 타입 사용을 검토한다. 단순히 타입을 넓히기 위해 부모 타입을 사용하지 않는다.

- 인터페이스 분리 원칙 : 인터페이스가 필요한 경우 사용자가 필요로 하는 기능별로 계약을 나누고, 사용하지 않는 기능에 의존하게 하지 않는다.

- 의존역전 원칙 : 구현 교체나 의존성 분리가 필요한 경계에서 추상화에 의존하도록 검토한다.
```

## 의존성과 통신
- 전역에서 하나의 인스턴스가 필요하고 생성·종료 책임이 명확한 경우에만 `Singleton`을 검토한다. 관리자라는 이름만으로 적용하지 않으며, 필요한 참조를 전달할 수 있다면 그 방식을 우선 검토한다.
- 대상이 명확한 단순한 통신은 직접 호출할 수 있다. 발행자가 구독자를 알 필요가 없거나 복수 구독자에게 알릴 필요가 있을 때 `Action` 등 이벤트·대리자를 검토한다.

- 신규 타입 생성과 추가 추상화는 [승인 범위](<../Safety/Approval Convention.md>)를 따른다.
- 참조 획득은 [참조 관리](<../Code/Reference Convention.md>), 구독·해제는 [이벤트 수명](<../Code/Event Convention.md>)에서 관리한다.
- 단순 취향 차이로 기존 구현을 리팩토링하지 않는다.
