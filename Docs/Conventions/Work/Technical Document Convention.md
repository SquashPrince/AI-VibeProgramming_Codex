# 기술 문서 컨벤션

> 상태: 공통 운영 기준. <br>
> 대상: Unity/C# 기반 AI 보조 개발. 기존 승인 규칙과 사용자 확정 사항을 유지한다.

## 목적
구현한 기술의 원리 · 구현 과정 · 개선점을 코드 공개 없이 기록한다.

## 작성 대상 · 위치
- 기능 단위로 한 문서를 작성한다. 양식은 [기술 문서 템플릿](<../../Templates/TechnicalDocument.md>)을 따른다.
- 문서 위치 : `Docs/Technical/<기능영역>/<문서명>.md`
- SVG 위치 : `Docs/Technical/<기능영역>/Images/<그림명>.svg`
- 기능영역 · 문서명 · 그림명은 영문 PascalCase 로 적는다. (예: `Player/WallJump.md`)

## 작성 절차
- 목차와 섹션별 핵심 한 줄을 먼저 보고하고 승인을 받는다. 본문 전체를 채팅에 먼저 보여주지 않는다.
- 작성 중 사용자에게 기대 동작과 기능을 만든 목적부터 묻고, 주요 설계 선택의 이유와 활용 의도를 확인한다. 답변이 필요한 항목은 하나씩 질문하며, 이미 답한 내용을 다시 묻지 않는다.
- 승인되면 파일을 생성한다.
- 수정 요청은 바뀌는 부분만 고친다. 고칠 내용을 짧게 알리고 승인을 받는다.
- 내용은 실제 코드 · 작업 기록 · 사용자 답변으로만 채운다. 확인하지 못한 내용은 `미정` 또는 `미검증` 으로 적는다.
- 사용자가 설명한 의도와 판단은 의미를 바꾸지 않고 기록한다. 실제 구현이나 검증 결과와 차이가 있으면 차이를 알리고, 의도와 확인된 사실을 구분해 적는다.
- 글만 길게 나열하지 않고 동작 흐름을 도식과 짧은 설명으로 함께 보여준다. 본문은 코드명·클래스명보다 기능이 어떻게 동작하고 어떻게 만들어져 활용되는지 중심으로 쓴다.
- `A가 아니라 B다`처럼 불필요한 대조나 모호한 중립 표현을 피하고, 확인된 동작과 사용자 결정을 직접 서술한다.
- 세부 설정 수치(거리 · 각도 · 범위 등)는 적지 않고, 어떤 동작을 하는지만 설명한다.

## 보안
- 본문과 다이어그램에 코드 조각, 직접 작성한 메서드 · 변수 이름, 파일 경로를 적지 않는다.
- 직접 작성한 스크립트 이름은 `구성 요소` 섹션에서만 쓰고, 본문에서는 역할로 부른다. (예: `카메라 추적 기능`)
- Unity · 외부 패키지 · 플러그인의 공개 기능 이름은 그대로 쓸 수 있다. (예: `CharacterController`, Cinemachine `Follow`)
- 비밀 값은 [민감정보 컨벤션](<../Safety/Sensitive Information Convention.md>)을 따른다.

## 다이어그램
- 기본 형식은 Mermaid `flowchart` 이며, 문서 안에 직접 작성한다.
- flowchart 로 표현하기 어려운 공간 · 기하 내용(각도, 궤적, 범위, 위치 관계 등)은 AGENT 가 SVG 를 이유와 함께 먼저 제안하고, 승인 후 작성한다.
- 노드 이름과 그림 안 글자도 `보안` 규칙을 따르고, 한국어로 적는다. (예: `UpdateFollow()` ✗ → `카메라 위치 갱신` ○)

### SVG 작성 규칙
- `viewBox` 를 지정한다.
- 외부 리소스(이미지 · 글꼴 링크)와 스크립트를 넣지 않는다.
- 밝은 · 어두운 화면에서 모두 읽히도록 배경색을 직접 지정한다.
- 문서에는 상대 경로로 삽입한다. (예: `![카메라 시야](Images/CameraView.svg)`)
- 작성 후 AGENT 가 Edge 헤드리스로 PNG 렌더링해 글자 겹침 · 어긋남을 직접 확인하고 고친 뒤, 사용자에게 확인을 요청한다.
- 확인용 PNG 는 프로젝트 밖 임시 폴더에 저장한다.

## 갱신
- 기능이 바뀌면 [업무 규칙](<../../Codex/WorkflowRules.md>)의 `6. 문서 / 다이어그램 반영` 단계에서 관련 기술 문서를 함께 갱신한다.
- 기존 방식이 바뀐 경우, 바뀌기 전 방식은 해당 문서의 `기존 방식과 비교` 섹션에 남긴다.
