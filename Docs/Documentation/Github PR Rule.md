# Pull Request 작성 규칙

> Github Pull Request를 작성할 때의 규칙.

> PR 작성 양식은 [PR 템플릿](<../Templates/PullRequest.md>)을 참고.

> 해당 문서는 제목, 각 섹션, Label에 대한 작성 규칙을 정의한다.

## 0. 작성 절차

- `확인 결과` 섹션은 실제로 수행해 확인한 항목만 체크한다. 실행하지 않은 항목은 미검증으로 남긴다. 수행자는 별도로 적지 않는다.
- PR 초안을 사용자에게 보여주고 승인 후 등록한다. 등록 후 PR 번호를 보고한다.
- PR의 Assignees는 [Git 컨벤션](<../Conventions/GitHub/Git Convention.md>)의 협업 기준을 따른다.

## 1. 제목

- 제목은 `[태그] 구현 내용` 형식으로 작성
- 태그는 [Git 컨벤션](<../Conventions/GitHub/Git Convention.md>)의 Commit 종류를 따른다.
- 구현 내용은 구현한 내용 요약을 명사형으로 끝나도록 작성한다.
- 제목에는 괄호 `()` 를 사용하지 않는다.
- 예시 : 
    ```markdown
    [Feat] 플레이어 이동 및 점프
    ```

## 2. 관련 Issue

- 해당 PR 혹은 branch 와 관련이 있는 Issue 를 적어 Merge 시 자동으로 Closes 될 수 있게 한다.
- 예시 :
    ```markdown
    ## 관련 Issue
    - Closes #1
    ```

## 3. 구현 내용

- 작업에서 구현한 내용과 해당 작업을 다른 사람이 확인해 볼 수 있는 사항에 대해 적는다.
- 함께 수행한 작은 단위 작업이 있으면 본 작업과 구분해 변경 이유·내용·검증 결과를 적는다. 작업과 직접 관련이 없어도 생략하지 않는다.
- 리스트로 작성하며, 불필요한 표현을 제거해 간결하게 작성한다.
- 예시 :
    ```markdown
    ## 구현 내용
    - 플레이어 이동 구현, WASD로 이동 Space키로 점프 할 수 있다.
    - 플레이어 이동 방식을 CharacterController 로 구현.
    - ...
    ```

## 4. 영향받는 파일

- 구현하며 생성/수정 하게 된 파일이나 코드에 대해 왜 그렇게 하였는지를 포함하여 적는다.
- 각 파일에 대한 이유는 들여쓰기를 한 후 리스트로 작성하며, 불필요한 표현을 제거해 간결하게 작성한다.
- 리스트로 작성하며, 특정 경로의 파일에 어떤 작업이 이뤄지는지 기재한다.
- 예시 :
    ```markdown
    ## 영향받는 파일
    - `Assets/Scripts/PlayerController.cs` 수정
        - 'player' -> '_player' 로 필드명 변경
    - `Assets/Scripts/Core/IDamageable.cs` 수정
        - TakeDamage 매개변수를 int -> float 로 변경
        - 프로젝트 특성상 int 보다 float 계산이 더 나은 방향이라고 판단
    - `Assets/Scripts/Monster/Goblin.cs` 생성
        - 실제 동작 확인을 위한 고블린 생성
    - `Assets/Scripts/Monster/Monster.cs` 수정
        - 임시 동작 구현 부분 삭제, 실제 동작에 맞게 수정
    - ...
    ```

## 5. 확인 결과

- 관련 Issue 의 `완료 조건(DoD)` 를 기본으로 작성하며, 추가 사항이 있을경우 이어서 적고 결과를 표시한다.
- 만약 관련 Issue 가 없을 경우 사용자에게 확인을 받아 작성한다.
- 예시 :
    ```markdown
    ## 확인 결과

    - [X] `PlayerController` 객체와 `MonsterController` 객체가 `IDamageable` 인터페이스를 통해서만 데미지 판정을 주고받는다.
    - [X] `IDamageable.TakeDamage(DamageInfo info)` 메서드를 통해 공격을 시도한
    객체에서 공격을 받는 객체로 `DamageInfo` 구조체가 전달된다.
    - [ ] 공격을 받는 객체의 `DamageInfo` 로그 출력 확인 — 미검증
    - [ ] 유니티 에디터에서 새 컴파일 오류가 없는지 확인 — 미검증
    - [ ] `Goblin.cs`의 실제 동작 확인 — 미검증
    ```

## 6. 특이사항

- 아래의 사항에 해당되지 않으면 이 섹션은 기재하지 않는다.
    1. 사용자가 명시적으로 언급한 특이사항이 있는 경우
    2. 구현한 내용을 다른 팀원이나 담당에서 꼭 알아야 하는 사항이 있는 경우
    3. 구현된 범위가 크고 넓어 따로 설명이 필요하다고 판단한 경우
- 특이사항 작성시 모호하거나 애매한 경우 사용자에게 확인을 받아 작성여부를 결정한다.
- 절대 임의로 작성하거나 거짓, 과장된 내용을 작성하지 않는다.
- 필요할 경우 참고용 사진이나 영상을 사용자가 직접 제공하도록 유도한다.

## 7. 기타

### Label

Label은 아래 항목중 하나를 채택하여 걸어둔다.
- Bug : 오류 메시지가 뜨거나 무언가 예상과 다르게 작동할 때
- Docs : 문서관련 작업을 수행
- Feature : 새로운 기능을 추가
- Improvement : 기존 기능을 개선하거나 보수하는 작업
- Art : 그래픽 및 에셋 제작
- UI/UX : UI 및 사용자 경험 작업
- Refactor : 기능의 변화를 주지 않는 코드 개선
- Chore : 기타 유지보수 작업, 설정 및 패키지 정리
