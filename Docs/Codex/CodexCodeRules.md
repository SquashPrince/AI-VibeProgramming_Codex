# Codex 행동 규칙

> Codex 가 이 프로젝트에서 반드시 따라야하는 행동 규칙

---

## 행동 원칙

### 1. 사고 우선 (Think Before Coding)

> 가정을 숨기지 말고, 결과에 영향을 주는 미확정 사항은 확인한다.

- 요구 동작·데이터 구조·외부 패키지·공개 API·완료 조건에 영향을 주는 미확정 사항은 관련 대안과 영향을 설명하고 사용자에게 확인받는다. 해당 결정에 의존하지 않는 승인 작업은 계속할 수 있다.
- 새 요청이 이미 승인된 구현 방식과 충돌하면 기존 승인 기록·현재 구현·새 요청에서 확인한 근거와 충돌 지점을 보고한다. 기존 방식을 유지하며 새 요구를 구현하는 방법과 그 이유, 새 요청의 방식으로 구현할 때 기존 동작·구조에서 바뀌는 점과 그 이유를 비교한다. 확인하지 못한 영향은 가정으로 표시하고, 사용자 선택을 받은 뒤 진행한다.
- 모든 컨벤션에 공통으로, 적용 기준이 모호하거나 별도 판단이 필요한 경우 모호한 점과 선택지를 사용자에게 설명하고 답변을 받은 뒤 해당 작업을 진행한다. 이미 답변받은 동일한 조건은 재질문하지 않는다. 해당 결정에 의존하지 않는 승인 작업은 계속할 수 있다.
- 승인 범위 안에서 요구 동작과 완료 조건을 바꾸지 않는 지역 변수·문법·기존 컨벤션에 맞는 세부 구현은 에이전트가 판단한다. 이 선택마다 질문하거나 승인을 반복 요청하지 않는다.
- 더 단순한 방법이 보이면 사용자에게 알린다.
- 코드를 읽기만 하고 세운 결론은 "미검증"인 상태로 표기한다.

### 2. 단순한 우선 (Simplicity First)

> 문제를 푸는 최소한의 코드만 작성한다.

- 요청범위 밖의 기능을 추가하지 않는다.
- 한번만 쓰는 코드에 추상화를 도입하지 않는다.
- 요청하지 않은 "확정성" 이나, "가능성"을 미리 만들지 않는다.
- 일어날 수 없는 상황을 위한 예외처리를 작성하지 않는다.

### 3. 외과적 변경 (Surgical Change)

> 필요한 부분만 건드린다.

- 인접 코드, 주석, 포맷팅을 임의로 "개선"하지 않는다.
- 구동에 문제가 없는 코드를 리펙토링 하지 않는다.
- 본인 변경 때문에 쓰이지 않게 된 변수, 함수는 정리한다. 원래있던 죽은 코드는 보고만 한다.

**판단 기준** : 변경을 가하는 모든 행위는 사용자의 결정에서 직접 나와야한다.

### 4. 검증 가능한 목표 (Goal-Driven Execution)

> 성공 기준을 먼저 정하고, 확인될 때까지 진행한다.

- 만약 여러 단계로 작업을 나눠야 할 경우를 포함한 모든 상황에서 작업 계획을 브리핑한다.

```
1. [단계명] -> 확인 : [확인 항목], [확인 항목]
2. [단계명] -> 확인 : [확인 항목], [확인 항목]
3. [단계명] -> 확인 : [확인 항목], [확인 항목]
....
```

---

## 작업 범위 규칙
- 요청/승인받은 파일과 기능 외의 코드는 수정히지 않는다.
- 다른 파일에서 문제를 발견하면 보고만 하고 수정하지 않는다.

---

## 기능 구현 착수 규칙

> 기능 구현을 요청받으면 바로 작업하지 않고, 아래 형식으로 먼저 **브리핑**한 뒤 **승인**을 받고 착수한다.

```
## 구현 브리핑 : [기능명]

**작업 범위**
(구현 내용 요약)

**생성/수정 파일**
- 생성 : 
    - 파일 경로(역할)
    - ...
- 수정 : 
    - 파일 경로(변경 내용)
    - ...

**작업 순서** (`4. 검증 가능한 목표 (Goal-Driven Execution)`의 포맷)

1. 단계 1
2. 단계 2
...

진행할까요?
```

문서와 오타 등 코드가 아닌 단순 수정은 브리핑하지 않는다.


## 응답 규칙

- 소스코드의 주석은 한국어로 작성한다.
- 변수, 함수, 클래스 이름은 [관련 컨벤션 폴더](<../Conventions/Code>)를 따른다.
- 불필요한 코드, 쓰지 않는 변수, 빈 메서드는 만들지 않는다.
