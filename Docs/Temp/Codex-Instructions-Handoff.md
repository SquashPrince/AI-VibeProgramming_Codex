# Codex 지침 개선 작업 인수인계

갱신일: 2026-11-03

## 이 문서의 역할

다른 컴퓨터의 같은 프로젝트에서 Codex 지침 개선 결과를 이어받기 위한 상태 기록이다. 실제 규칙의 단일 출처는 `AGENTS.md`, `Docs/`의 해당 규칙 문서와 `.agents/skills/`의 스킬이다. 이 문서의 요약보다 실제 파일 본문을 우선한다.

## 현재 상태

- 이번 지침·컨벤션 검토는 완료됐다. 사용자는 각 변경을 순서대로 승인했고, 마지막 전체 점검에서 추가로 필요한 문서 수정을 찾지 못했다.
- `AGENTS.md`는 지침 진입점이다. 세션 시작 시 상시 로드 문서 4개의 실제 파일을 읽고, 작업에 필요한 온디맨드 문서만 추가로 읽는다.
- 상시 로드 문서는 `Docs/Codex/AgentCommonRules.md`, `Docs/Codex/CodexCodeRules.md`, `Docs/Codex/WorkflowRules.md`, `Docs/Project Values.md`다. 유지 결정은 승인됐다.
- `README.md`에는 확인된 프로젝트 소개와 개발 환경 표만 적혀 있다. 정식 게임 제목·콘셉트·실행 방법은 추측해 추가하지 않았다.
- `.gitignore`에서 `/Docs/` 무시 규칙을 제거했다. 실제 Git 추적·동기화 여부는 사용자가 확인하기로 했다.
- 이 작업 공간에는 `.git` 디렉터리가 없어 브랜치·작업 트리·추적 상태를 확인하지 못했다. 다른 컴퓨터에서는 실제 Git 상태를 새로 조회한다.
- Unity 실행 검증은 수행하지 않았다. 이번 작업의 검증은 문서 본문·참조·규칙 일치 여부에 한정된다.

## 핵심 합의

### 승인과 작업 흐름

- 파일 수정·삭제 전 사용자 승인을 받는다. `main`·`main-dev`에서는 작업 브랜치로 전환될 때까지 수정 작업을 진행하지 않는다.
- 브랜치 생성·전환, Commit·Push·Merge는 사용자가 직접 한다. 에이전트는 브랜치 이름, Commit 시점·메시지 초안·포함 파일을 안내한다. Issue·PR은 스킬 절차에 따라 에이전트가 작성·등록한다.
- 브리핑에는 목표, 근거와 이유, 구현 대안과 영향, 수정·생성 파일 목록, 검증 계획을 적는다. 이미 승인한 선택은 다시 묻지 않는다.
- 새 요청이 기존 승인 방식과 충돌하면 승인 기록·현재 구현·새 요청의 근거를 제시하고, 기존 방식 유지안과 새 방식 적용 시 변경점을 비교해 사용자 선택을 받는다.
- 독립적인 기능·완료 조건이 없는 작은 수정은 다음 작업과 관련이 없어도 승인 후 그 작업의 브리핑·PR에 구분해 포함한다. 작은 작업만을 위한 별도 PR은 만들지 않는다. 다음 작업 없이 단독 마무리가 필요한 예외는 사용자에게 질문한다.

### 구현과 검증

- 사용자가 명시하지 않았어도 관련 Unity 기본 기능·기존 에셋을 검토해 적합하면 제안한다. 사용자가 방법을 지정했어도 더 적합한 방법을 찾으면 근거별 목록으로 역제안한다. 에셋 예시는 선택 범위를 제한하지 않으며 패키지·설정의 실제 사용 가능 여부를 확인한다.
- 이름은 요청 표현·입력 키를 그대로 고정하지 않고 기능·역할 기준으로 정한다. 확인용·테스트용 이름도 임의 확정하지 않고 제안해 확인받는다.
- 분리 검토는 실제 코드 줄 수가 메서드 40줄 이상, 클래스 250줄 이상일 때 시작한다. 빈 줄·주석만 있는 줄·표시용 괄호만 있는 줄은 제외한다. 줄 수만으로 분리하지 않는다. 지나치게 세분화된 짧은 클래스의 병합도 책임과 관리 비용을 보고 검토한다.
- `Update()`의 전체 동작이 단일 표현식 한 줄이면 식 본문으로 직접 쓸 수 있다. 그 외에는 내용을 별도 메서드로 분리한다. 초기화·캐싱 분리는 `Formatting Convention.md`의 기준을 따른다.
- 검증은 변경 종류에 맞춰 수행한다. 코드 변경은 컴파일·영향 동작을 확인하고, 문서만 변경했으면 내용·경로·변경 범위를 확인한다. 미실행 항목은 미검증으로 남긴다.

### 문서·운영

- `Project Values.md` 또는 `Project Configuration.md`와 실제 설정이 다르면 차이를 항목별로 보고하고, 해당 문서 값을 초기화해 다시 설정할지 사용자에게 묻는다. 답변 전에는 초기화하지 않는다.
- 기술 문서는 기대 동작·활용 목적·주요 설계 이유를 사용자에게 하나씩 확인해 기능 중심으로 작성한다. 도식과 짧은 설명을 함께 쓰고, 사용자 의도와 확인된 구현이 다르면 구분해 기록한다.
- 외부 업무 도구는 선택 사항이다. 최초 사용 여부를 확인하고, 없으면 동기화를 생략한다. 이후 도입하면 등록한 뒤 갱신 대상으로 삼는다.
- 작업 일지를 작성한 뒤 추가한 작업은 기존 일지를 수정하지 않고 다음 날 작성하는 일지에 포함한다. 지난 날짜의 누락 일지는 한 번만 질문하며 기록이 없는 날은 생략한다.
- 민감정보 노출이 의심되면 값을 재출력하지 않고 먼저 사용자에게 알린다.

## 다음 컴퓨터에서 확인할 것

1. 실제 `AGENTS.md`와 상시 로드 문서 4개를 읽는다. 이 요약만으로 규칙을 적용하지 않는다.
2. 현재 브랜치와 작업 트리 상태를 읽기 전용으로 확인한다. `main`·`main-dev`라면 작업 브랜치로 바뀔 때까지 수정하지 않는다. Git 상태 변경 명령은 직접 실행하지 않는다.
3. `Docs/`, `.agents/skills/`, `.agents/state/`, `AGENTS.md`, `README.md`, `.gitignore`가 실제로 전달됐는지 확인한다. `.gitignore` 변경만으로 이전에 무시된 문서가 자동 추적되었다고 판단하지 않는다.
4. `.agents/state/deferred-small-tasks.json`과 `.agents/state/worklog-review-state.json`을 읽는다. 갱신 시 두 파일 모두 빈 상태였으며, 다른 컴퓨터에서는 실제 상태를 우선한다.
5. 사용자 요청이 있으면 해당 온디맨드 문서와 스킬을 읽고 진행한다. 이번 검토에서 이미 승인한 지침 변경을 재질문하거나 일괄 재적용하지 않는다.

## 확인 범위와 주의

- 마지막 점검에서 `Docs/`의 Markdown 문서 34개, 프로젝트 스킬 8개, `AGENTS.md`, `README.md`의 역할과 주요 참조를 대조했다. 로컬 링크 점검에서 실제 문서로 향하는 깨진 경로는 찾지 못했다. 외부 URL과 예시 SVG 경로는 링크 검증 대상이 아니었다.
- `Docs/Temp/작업지시서.md`는 과거 Commit 스킬화 작업의 기록이다. 새로운 작업 지시로 취급하지 않는다.
- 실제 Git 추적 상태, 다른 컴퓨터로의 동기화, Unity 실행 결과는 이 인수인계에서 확인되지 않았다.

## 재개 요청 예시

> 현재 프로젝트의 `AGENTS.md`와 상시 로드 문서를 실제 파일로 확인하고, `Docs/Temp/Codex-Instructions-Handoff.md`의 상태 기록을 참고해줘. 먼저 Git 브랜치·전달된 파일·보류 작업 기록을 확인한 뒤 이번 요청을 진행해줘.
