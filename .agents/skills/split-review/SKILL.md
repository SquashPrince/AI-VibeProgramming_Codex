# 기능 분리·병합 검토

> 이 스킬은 절차와 멘트 규격만 정의한다. 규칙의 원본은 아래 문서이며, 내용을 이 파일에 복사하지 않는다.
>
> 이 스킬은 검토와 보고만 한다. 사용자 승인 전에는 코드를 분리·병합·수정하지 않는다.

## 참조 문서 (필요 섹션만 읽는다)

- 분리 기준 · 보고 양식 : `Docs/Conventions/Code/Formatting Convention.md` 의 `기능 분리`, `주석`
- 병합 기준 · 작업 전 보고 : `Docs/Conventions/Work/Architecture Convention.md` 의 `설계 원칙`, `작업 전 보고`
- 신규 파일 · 타입 승인 : `Docs/Conventions/Safety/Approval Convention.md`

## 절차

1. 참조 문서의 필요 섹션을 읽는다.
2. 분리 검토라면 원본 문서의 실제 코드 줄 계산법으로 대상 메서드·클래스의 줄 수를 센다. 측정 방법과 결과를 함께 적는다. 기준 미만이면 짧게 보고하고 끝낸다. (멘트 ①)
3. 병합 검토라면 작은 클래스들의 책임·변경 이유·연결과 관리 비용을 확인한다. 클래스 수나 길이만으로 병합을 결정하지 않는다.
4. 분리·병합할 대상, 이유, 유지할 동작과 영향받는 파일을 정리한다. 기존 동작과 외부 호출에 미치는 영향을 보고한다.
5. 제안의 근거와 장단점을 적고, 분리는 `기능 분리 검토` 양식으로, 병합은 `작업 전 보고` 기준으로 사용자에게 보고해 승인을 기다린다.
6. 승인되면 `Docs/Codex/WorkflowRules.md` 의 `3. 브리핑` 절차로 넘어간다. 반려되면 코드를 그대로 둔다. (멘트 ②)

## 멘트 규격

① 기준 미만

```
[기능 분리] 검토 대상 아님
- 대상 : <클래스.메서드>
- 실제 코드 줄 수 : N줄 (빈 줄·주석만 있는 줄·표시용 괄호만 있는 줄 제외, 기준 <메서드 40 / 클래스 250>줄)
```

② 검토 종료

```
[기능 분리·병합] <승인 → 브리핑으로 진행 / 반려 → 변경 없음>
```
